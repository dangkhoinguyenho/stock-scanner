## Non-negotiable domain rules (enforced everywhere, not just where convenient)

1. Never output a bare verdict ("buy", "bullish"). Always show the evidence: comparable historical events, base rate/win %, avg/median return, max favorable/adverse excursion, confidence.
2. Direction, magnitude, and speed are always separate outputs — never blended into one score.
3. Use abnormal/relative returns (vs. QQQ or the relevant index), not raw price moves.
4. Every analysis or backtest must be actively checked for look-ahead bias (only use information actually available at the time) and survivorship bias (the historical universe must reflect what was actually tradable at each point in time, including delisted/acquired/bankrupt companies).
5. Respect option expiration — a catalyst that happens after an option's expiration is not a driver for that option.
6. Start simple (historical similarity + base rates, Phase 5) before ML (Phase 6); any added complexity must be justified by a demonstrated out-of-sample improvement.
7. Event importance is ticker/industry-specific — never assume "good news = bullish" as a generic rule; let the data say which events matter for which tickers.
8. Every module states which of the 10 phases above it belongs to.

## Prior work (context, not code we're reusing directly)

Kenny built pieces of this system before, across six separate repos on his laptop (Trading Bot, Options Project, ReadNewsV2, Read News Bot, BustingHeadline, RobinhoodTrading — full detail in the Claude project doc `claude/existing-assets-audit.md`). We're rebuilding clean rather than merging those repos, but keeping them connected as reference: when we reach a phase one of them already attempted, we check what's there and rewrite the useful parts to fit this repo's structure and rules, rather than starting purely from scratch each time. Two findings from that prior work are worth carrying forward as motivation, not as validated conclusions:

- Trading Bot's 1000-ticker 2025 backtest: equity PnL +1.92R but options PnL -16.21R on the same signals — a real example of why Phase 7 (options layer) has to be its own model, not a pass-through of the stock-direction prediction.
- ReadNewsV2's `pattern_learner.py` already computed win-rate/avg-return by (sector, news_type) — the right idea (Phase 4/5), but on raw returns rather than abnormal returns (violates rule 3 above) and mostly on sample sizes too small to trust (many news types had n=1). A useful shape to rebuild correctly, not numbers to trust as-is.

- **2026-09-12** — Built Phase 2 (event normalization) as one batch, per a new working agreement with Kenny: build + self-test a full coherent unit of work, then bring one consolidated checkpoint instead of checking in after every file. `events/classifier.py` turns raw news/SEC filings/economic observations into a new `events` table (added to `storage/database.py`, keyed on `(source_type, source_id)` — a natural key back to the raw row, making re-classification idempotent by design) with a category, an optional **hypothesized** direction, and a `classification_reason` string on every single row explaining exactly which keyword(s) fired — this is rule 1 (never a bare verdict) applied at the classification layer itself, not just the final output. Three deliberate deviations from the letter of project-spec.md worth flagging explicitly: (1) rule-based keyword matching, not an LLM as originally envisioned in section 10 — per rule 6 (start simple, justify complexity later) and to avoid a per-article cost before proving keyword rules are actually insufficient; (2) no text-derived "magnitude" or "novelty" score, even though the spec's example event record has them — a magnitude number guessed from headline language with no calibration would be a made-up number dressed as data, and real magnitude is measured from actual price reactions in Phase 4 anyway; (3) several categories (Pricing, M&A, Product) get NO direction hypothesis at all, on purpose — the spec's own Netflix pricing example (section 21: could be bullish from revenue or bearish from churn) shows why guessing would violate rule 7. SEC filing classification is coarse by a real, flagged limitation: EDGAR's submissions API only gives form type, not item codes, so every 8-K lands in one bucket regardless of what it's actually about, and Form 4 (insider transactions) doesn't carry buy/sell direction without parsing the filing document itself — not done yet. Added `get_all_news_articles`/`get_all_sec_filings`/`get_all_economic_observations` to `database.py` so the classifier can process everything collected without needing to know which symbols/series exist in advance. 68 tests passing in Claude's sandbox; pending Kenny running the real suite + a live classification pass on his actual collected data.

- **2026-09-12** — Picked data sources for Phase 1's four non-options collectors, each verified against real data on Kenny's machine, not just fake test fixtures: market data via **yfinance** (no key, no cost — chosen over Alpha Vantage to avoid its free-tier rate limits); SEC filings via **SEC EDGAR**'s public submissions API (no key, just a required User-Agent header); economic calendar via **FRED** (free key, official St. Louis Fed source — covers CPI/PPI/unemployment/payrolls/GDP/Fed funds rate); news via **Finnhub**'s free tier (free key, 60 req/min, a real documented `company-news` endpoint rather than scraping). Two flagged, not-yet-solved gaps: the economic calendar stores each observation's current value, not the as-first-published vintage (a real look-ahead-bias risk per rule 4, deferred rather than hidden); news collection is company-specific only, not the industry-level news the spec also wants (section 6). Options data collector still not started — deferred pending a decision on a historical options data source, since free tiers generally don't cover historical options chains the way they do price/news/filings/macro data.
- **2026-09-12** — Wired the options collector into a daily unattended job: `config.py` gained a `watchlist` setting (`WATCHLIST` env var, default `NFLX`), `jobs/daily_options_snapshot.py` loops over it calling `collect_and_store` per symbol with each symbol wrapped in its own try/except (one bad ticker can't kill the run), and `run_daily_options.bat` + a `Register-ScheduledTask` PowerShell command schedule it through **Windows Task Scheduler** at 5:00 PM Pacific (Kenny's time zone; well after the 4:00 PM ET market close) — a real OS-level scheduler, not something that depends on a Claude session being open, since this job has to run every day indefinitely with no recoverable backfill for a missed day. Deliberately did not use Claude's own scheduled-task/trigger mechanism for this: it would spin up a fresh cloud session with no access to Kenny's local Python environment, venv, or `.env` keys, and this repo's cloud sandbox can't reach yfinance at all (network egress blocked) — the job has to run where the data actually gets collected. Used `-WakeToRun` (wakes a sleeping laptop to run the job) and `-StartWhenAvailable` (catches up as soon as the laptop is next on, if 5 PM was missed) per Kenny's ask to keep this running even when his PC isn't actively on — honestly flagged limit: neither helps if the laptop is fully powered off for a stretch of days, since no software can wake a machine that isn't running; those specific days are a real, permanent gap, same as any other missed day. Logging is handled at the batch-script layer (`>> logs\daily_options.log 2>&1`) rather than duplicated inside Python, so there's one place responsible for where logs live.
- **2026-09-12** — Built the options data collector (`collectors/options.py`) via **yfinance** as a live-only snapshot: every call/put contract across every expiration currently listed, with price/bid/ask/volume/open interest/implied volatility, stored keyed on `(contract_symbol, as_of_date)` so the same contract accumulates one row per day rather than being overwritten — this is intentionally different from every other Phase 1 table, which overwrite-on-conflict. Confirmed real limitation, not a bug to fix later: no free source (yfinance included) exposes a *historical* options chain, only the current one — so this collector cannot backfill the past and only starts building real history from whatever day it's first run onward. To work around that gap for research in the meantime, also built `analysis/options_pricing.py` (Phase 7): a Black-Scholes theoretical pricing engine (stdlib `math` only, no new dependency) that estimates what an option would have been worth on a past date using stock price history + the risk-free rate (FRED). It substitutes **realized volatility** (computable from price history) for **implied volatility** (a real market-observed quantity that cannot be reconstructed from price history alone — see that module's docstring for the full reasoning, e.g. IV crush around earnings). Every value it returns is explicitly labeled a theoretical estimate, never presented as a real historical price, per rule 1.
